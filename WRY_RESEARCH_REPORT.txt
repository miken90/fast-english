Q1: wry crate latest version, API for frameless/transparent on Windows?
─────────────────────────────────────────────────────────────────────────
✓ ANSWER: Yes, fully supported.
  Version: wry 0.54.3 (latest stable)
  Dependency: tao 0.34.6 (window manager)
  
  CODE PATTERN:
  .with_decorations(false)      // Remove title bar
  .with_transparent(true)        // Enable transparency
  .with_always_on_top(true)     // Popup behavior
  .with_background_color((0,0,0,0))  // RGBA transparent

  LIMITATION: Windows 7 NOT supported (alpha ignored)
  REQUIREMENT: Windows 8+ only


Q2: wry IPC - How to communicate Rust ↔ JavaScript?
─────────────────────────────────────────────────────────────────────────
✓ ANSWER: Two patterns supported.

  PATTERN A (Recommended):
    JS → Rust: window.ipc.postMessage(JSON.stringify(data))
    Rust → JS: webview.evaluate_script("window.dispatchEvent(...)")
  
  PATTERN B (Alternative):
    Use custom protocol for static assets
    register with_custom_protocol("wry", handler)

  IPC Handler signature:
    .with_ipc_handler(move |request| {
        let body = request.body();  // JSON string from JS
        // Process and route to tokio async tasks
    })


Q3: wry + tao window management - positioning, resizing, show/hide?
─────────────────────────────────────────────────────────────────────────
✓ ANSWER: Full programmatic control via tao API.
  
  KEY METHODS:
    window.set_inner_size(LogicalSize)
    window.set_outer_position(LogicalPosition)
    window.set_visible(bool)
    window.set_always_on_top(bool)
    window.focus()
  
  SUPPORTS:
    - Positioning near cursor
    - Dynamic resizing
    - Show/hide without closing
    - Always-on-top behavior


Q4: wry vs tauri-lite - is wry standalone sufficient? Binary size impact?
─────────────────────────────────────────────────────────────────────────
✓ ANSWER: Use wry ONLY. Tauri not needed.
  
  COMPARISON:
    wry only:    15-20 MB binary
    Tauri:       40-60 MB binary
  
  YOUR USE CASE:
    ✓ Only need popup, not full framework
    ✓ IPC via ipc_handler is straightforward
    ✓ No need for plugin system/auto-updater
  
  RECOMMENDATION: Skip Tauri overhead


Q5: Can wry coexist with existing tokio runtime?
─────────────────────────────────────────────────────────────────────────
✓ ANSWER: YES, with proper threading pattern.
  
  KEY INSIGHT:
    tao EventLoop is blocking → must run on separate thread
    tokio runtime continues independently on main thread
  
  PATTERN:
    1. Spawn std::thread for tao EventLoop (blocks)
    2. Use Arc<Mutex<>> for shared state between threads
    3. Use EventLoopProxy::send_event() for signaling
    4. tokio continues in main thread (no blocking)
  
  INTEGRATION:
    .with_ipc_handler() uses blocking_send() → safe in sync context
    Route heavy work to tokio via mpsc channel

KEY FINDINGS & GOTCHAS
================================================================================

✅ WHAT WORKS:
  - Transparent backgrounds (W8+)
  - Borderless windows
  - Always-on-top behavior
  - Positioning & sizing
  - CSS backdrop-filter, SVG, animations, custom fonts
  - Bidirectional IPC (Rust↔JS)
  - Coexistence with tokio runtime

⚠️  GOTCHAS:
  1. Windows 7 transparency NOT supported
  2. IPC handler NOT Send/Sync → can't use async/await directly
     Solution: Use blocking_send() inside handler, route to mpsc
  3. WebView lifecycle must be managed (store in struct)
  4. tao EventLoop blocks → must be on separate thread
  5. Only Windows supported (use #[cfg(target_os = "windows")])
